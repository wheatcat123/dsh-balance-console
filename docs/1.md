## 二、逐轮开发记录

### 第 1 轮：基础余额读数（CMD 控制台风格）

**需求**：在对话输入框下方以 CMD 风格显示 API 平台余额；任务运行时实时更新；空闲时提供手动刷新；刷新频率以秒为单位可配置；提供登录接口并在首次登录后免登录。

**实现途径**：

- 定位到两个关键扩展点：`deepseekAccount`（Host 端账户服务）与 `conversation.composer.dock`（输入框卡片下方的 slot）。
- 数据源选型：官方 `GET https://api.deepseek.com/user/balance`，用 `DEEPSEEK_API_KEY` 鉴权。先实测确认该端点可用（返回真实余额），再动手写代码。
- 通信方案的关键弯路：最初按官方插件的做法用 **Typert Remote namespace** 暴露 Host 状态，结果客户端始终报 "Remote namespace 不可用"。排查后确认：我的插件在 profile 启动的极早期执行 `apply`，此时 `webServer`、`connection` 等服务**尚不存在**，因此 Remote 绑定无法建立。最终放弃 Remote，改为在 Host 端注册一条 HTTP 路由 `/api/balance-console/state`，鉴权复用 DSH 自身的 `connection.authorizeIndex`（未认证请求返回 401）。
- Host 半部：单文件 `index.js`，负责配置持久化（`~/.dsh/storages/dsh-balance-console.json`）、按用户设定的间隔轮询余额、变化即落盘。
- Client 半部：单文件 `client.js`，通过 `window.__ModuleLoader__.load` 注册到 `conversation.composer.dock`。

**验证**：在独立端口实例上以真实余额跑通；未认证 HTTP 401、已认证 200；截图确认 CMD 风格渲染。

### 第 2 轮：浮窗化（拖动、缩放、最小化、脱离对话框）

**需求**：增加尺寸调整与位置拖动；可最小化成正方形浮窗；把组件从对话框依赖中独立出来；仅当模型提供商为 DeepSeek 时显示。

**实现途径**：

- 从 `conversation.composer.dock` 迁移到 `shell.overlay`（框架级浮层），彻底摆脱 composer / session 面板的依赖。
- 用 `position: fixed` + CSS 变量实现可拖动、可缩放的浮窗，几何信息按窗口写入 `localStorage`。
- 最小化态为 56×56 方块，方块上直接显示余额数字；再次点击还原。
- provider 判定改为两级：Host 端读取会话的 `modelSelection` 投影给出权威 provider；界面上的模型选择器文本仅作正向确认。
- 调试中发现并修复两处自己引入的缺陷：把 provider 判断放在了 hooks 之前（会触发 hooks 顺序错误）；`null` 被 `Number()` 转成 `0` 导致默认位置跑到左上角。

**验证**：拖动（`x=1385→4`）、缩放（`472×118 → 564×190`）、最小化（`data-min=1`、58×58）逐项实测，并确认 `composerDockHasConsole: false`（确实不依赖输入框）。

### 第 3 轮：视觉与信息密度优化

**需求**：消除刷新闪烁（不要反复把标题改成黄色 FETCHING）；空闲预算色固定为 `rgb(162,162,162)`；赠送余额用青色 `rgb(43,234,178)` 且恒在最右；新增余额变化账单日志（最多 15 条、与余额行等宽对齐）；新增预期总预算与进度条。

**实现途径**：

- 闪烁问题：把刷新指示从"改标题文字"改为"`balance:` 左侧的 1ch 宽绿色方块闪烁"，标题文字保持稳定（`balance — IDLE / LIVE`）。这不是猜测——从你的真实账单数据里发现官方余额约每 60 秒结算一次，秒级采样 98% 是重复值，所以视觉上也不需要每次刷新都重画文字。
- 账单日志：Host 端在余额变化时追加一条记录（最多 15 条），Client 端用 flex 填充元素对齐——中间连号是一个 `flex:1` 的字符块，因此自动吃掉一行剩余宽度。实测账单行宽 542px = 余额行宽 542px。
- 进度条三段式：格内为绿色（已用）+ 灰色（`rgb(162,162,162)`，剩余）；超预算时绿色满格 + 白色溢出贴最右 + 青色赠送在白色左侧，形成（绿-白-青）顺序。

**验证**：像素级核对颜色与宽度；超预算态单独验证（绿色 238px + 白色溢出 112px，比例 189%）。

### 第 4 轮：异常状态界面与总开关

**需求**：为未填 key、网络错误、服务离线、key 非法四种情况开发友好界面；左下角加总开关；标题栏小点与余额方块同色。

**实现途径与放弃**：

- Host 端把失败分为 `invalid`（401/403）与 `network`（传输失败/超时）两类，并在状态里输出一个 `state` 字（`notConfigured / network / invalidKey / online`），Client 直接据此渲染。
- 未填 key：方块与 CNY 变红、静态；数值 0；进度条纯灰；日志位置贴"请点击设置以登录apikey"。
- 网络错误：方块红色闪烁；进度条采用**方案 2（scan 动效）** ——单条 `background-size:45%` 的红色渐变做 `background-position` 位移，只需一个 CSS keyframes，比呼吸灯更轻。
- key 非法：方块、进度条、CNY 变蓝 `rgb(78,149,255)`；方块闪烁、其余静态。
- 总开关注册到 `sidebar.footer.action`，状态存 `localStorage`。
- **放弃**：官方 API 预警余额（详见 §四）；DSH 离线检测界面（详见 §四）。

**验证**：用 Node 侧桩件逐个驱动 Host 状态机，确认四种 `state` 的输出；浏览器实测侧边栏开关切换与浮窗卸载/恢复。

### 第 5 轮：设置窗口、计价规则、消费回执（P1–P4）

**需求**：把设置迁移到独立窗口；新增计价规则与编辑器；新增单对话估价按钮与回执窗口；新增会话级回执与柱状图。

**实现途径**：

- **P1 共享浮窗外壳**：抽出 `FloatFrame`，统一拖动/缩放/最小化/置顶与"每窗独立几何记忆"；新增窗口挂载时自动置顶（此前两窗 z-index 都是 40，会互相遮挡）。设置内容迁入独立窗口。
- **P2 计价模型**：数据结构为"每条规则 → 工作日/节假日各一份 48 格峰位图 + 峰/谷各 3 个单价（命中/未命中/输出）"；峰谷互补，因此**只存峰**，谷是补集——这也天然满足你要求的"没有严格互补时按峰补齐谷"。估价为纯函数，Host 与 Client 保持同一算法。
- **P3 单对话估价**：注册到 `conversation.chat.turnTail`。
- **P4 跨会话聚合**：`sidebar.session.row.hover` 是 root 作用域，读不到别的会话的 tokenUsage。为此在 Host 端新增只读聚合：`sessionPersistence.list()/open(id,'read')` 直读任意会话的持久化日志并折叠，按日志 `revision` 做缓存——不加轮询、不加定时器。

**关键技术发现（三个坑）**：

1. `turnTail` 的 props **不含 tokenUsage**（只有 `{ turn, seq, openFile }`）；DSH 自己是靠内部的 `data.tokenUsage` 取用的，所以按轮用量必须在 Host 侧折叠日志。
2. `props.turn` 是 **`TurnLocation` 对象而非数字**（`{ turn, start, end, status, steps, data }`）。最初 `Number(props.turn)` 得到 `NaN`，按钮一直不渲染；改读 `props.turn.turn` 后立刻正常。这是本轮最耗时的一个坑。
3. **空闲会话没有 agent**：`ctx.agents.roots()` 只返回有活动 agent 的会话（实测 `roots=0`），所以聚合必须走 persistence 而不是 agent 注册表。

**验证**：回执窗口实测 `¥0.1309`（三行明细相加吻合）；聚合接口实测读到 49 个会话与逐轮明细；柱状图确认 10 根柱子。

### 第 6 轮：口径修正与会话入口

**需求**：自检单对话计价为何远低于真实值；把柱状图回执的入口移到会话标题旁，取消从左侧菜单浮窗取统筹数据。

**实现途径**：

- 自检结论：**折叠算法无误，错的是口径**。此前按钮按"单个 Turn"取数，而一次对话（整个 Session）跨越许多 step 与 request，每个 request 各报一份 usage。用你提供的真实数据复核——`110,025,856 命中 / 63,567 未命中 / 109,287 输出` 按你的规则（命中 0.04 / 未命中 2 / 输出 8）应为 **≈ ¥5.40**，而它恰好等于该会话**最后一轮**的估价，说明那组数字是"会话累计"而非"上一次对话"。
- 口径改为会话总额：`turnTail` 按钮改为显示会话总估价（标题 `session total`）。
- 新增标题旁入口：注册到 `conversation.session.header.actions`，文案 `会话估价「13.5140」￥`。
- 移除 `sidebar.session.row.hover` 的注册（按你的要求取消侧边浮窗统筹）。
- 顺手清理两个已无引用的辅助函数。

**验证**：`会话估价「13.5140」￥` 与 `对话估价「13.5140」￥` 同时显示会话总额；回执 `balance — RECEIPT ¥13.5140` 内 `conversations (10)` 柱状图 10 根柱子，横轴为用户消息首字（`T 为 做 越 太 太 越 # 越 开`），最高柱正是最后一轮的 ¥5.40。

## 四、明确放弃的功能

### 4.1 官方预警余额联动变红（放弃）

**需求条件**：只有当能从官方 API 取得"用户设定的预警余额"时才实现。

**放弃证据**：逐个实测候选端点，仅 `/user/balance` 返回 200：

```
/user/balance   HTTP 200   （仅返回 is_available 与各币种余额，无预警字段）
/user/info      HTTP 404
/user/settings  HTTP 404
/user/alert     HTTP 404
/user/notify    HTTP 404
/user/limit     HTTP 404
```

余额响应体只有 `currency / total_balance / granted_balance / topped_up_balance`，没有任何预警阈值字段；官方文档站在该网络环境下也无法解析。按你设定的规则（拿不到就立刻放弃），此功能**未写一行代码**。

### 4.2 DSH 离线检测界面（放弃）

**需求条件**：必须能判断"当前界面是否还有用"，若不能则立刻放弃。

**放弃证据**：这个界面本身就是 DSH 的 Web 产物。Host 进程下线时页面只剩 HTTP 层，前端拿不到任何"DSH 是否存活"的信号，反而会陷入自己检测自己的循环。按你设定的规则，此状态界面**未实现**。

### 4.3 其他被放弃的技术方案

| 方案 | 放弃原因 |
| --- | --- |
| Typert Remote namespace 通信 | 插件 `apply` 执行时 `webServer`/`connection` 尚未提供，namespace 无法建立；改用 HTTP 路由 |
| 定时高频采样（1/5 倍间隔） | 实测官方余额约每 60 秒结算一次，1 秒采样 98% 为重复数据，却把请求量提高 5 倍，违背"极致轻量"；改为事件驱动 |
| 左侧会话悬停卡统筹数据 | 你要求取消，改为标题旁按钮（第 6 轮） |
| 按单个 Turn 计价的按钮口径 | 会严重低估真实账单（见第 6 轮自检），改为会话总额 |
| 用 `ctx.agents.roots()` 做跨会话聚合 | 空闲会话没有 agent，实测 `roots=0`；改用 `sessionPersistence` |
